# Role-aware Shops, Tenants & Notifications — design amendment

**Relationship to the existing plan:** this is not a from-scratch design. `docs/superpowers/plans/2026-09-04-maduka-android-app.md` (Tasks 8–18) already specifies almost everything requested — dashboard/payment workflow, Properties, Tenants, Reports, Notifications ×2, Users, and all five Tenant-self screens — against the same design canvas the new `Maduka-standalone (2).html` mockup comes from. Most of it (Tasks 9, 12–18) was never implemented; Tasks 10–11 were implemented off-plan (full-screen forms + custom shop naming instead of bottom sheets + fixed A1–A10) and drifted from the plan's intended role separation. This document records the reconciliation decisions and the amendments needed on top of the original plan's task specs, then hands off to execution task-by-task.

## 1. Reconciliation decisions

1. **Bottom nav stays 5 tabs per role** (confirmed by both the original plan's Global Constraints and the new mockup — no change): Super Admin = Dashboard/Properties/Tenants/Reports/**Users**; Admin = Dashboard/Properties/Tenants/Reports/**Notifications**; Tenant = Dashboard/Payments/Details/History/Notifications. Tenant never gets a "Shops" or "Tenants" destination — the brief's "Shops tab — Tenant" and "Tenants tab — Tenant" sections map to Tenant's existing **Details** (own shop info) and **Dashboard/Payments/History** (own rent/payment info) respectively.
2. **Super Admin notifications: wire the existing top-bar bell** (`btnNotifications` in `activity_main.xml`, currently a "coming soon" `Toast` in `MainActivity.java:84-86`). It gets a real unread-count badge for all three roles. Tapping it: for Admin/Tenant, select the bottom nav's Notifications tab; for Super Admin (no such tab), open a full-screen `SuperAdminNotificationsActivity` (or fragment-in-dialog) reusing the same list UI/adapter as Admin's notifications, scoped to management/system events. Decided with the user 2026-09-06 over two alternatives (a 6th nav tab, or folding into Users) — this keeps the approved nav intact.
3. **Tenant registration is Super-Admin-only**, matching plan Task 11 and the mockup's "The super admin registers new tenants" copy. Current `TenantsFragment`/`TenantAdapter` show the register action to both roles with zero branching (its own doc comment says "no role branching needed" — that's the bug). Fix: gate the register button to `role == SUPER_ADMIN`; Admin sees the static note instead.
4. **Terminology stays as already resolved in the plan's Global Constraints**: `PaymentStatus` remains the English enum `PENDING/CONFIRMED/REJECTED`; Yupo/Inangoja/Hayupo are shared **display** vocabulary (`StatusPresentation`) reused for both payment status and tenant presence — no new "Inangoja" enum value, no change to `PresenceStatus{YUPO,HAYUPO}`.
5. **Custom shop naming and full-screen registration forms are kept** (the app's actual, more recent direction per git history and the mockup's own "shop names are placeholders" note) over the original plan's fixed-A1–A10/bottom-sheet approach. `AddShopActivity`, `RegisterTenantActivity` stay as Activities, not converted to the plan's `RegisterTenantSheet`/`RegisterAdminSheet` bottom sheets.
6. **Reports (plan Task 12) and Users (plan Task 14) are out of scope** for this pass — not mentioned in the brief, already at least stubbed/implemented, left untouched except where a shared component (e.g. `StatusBadgeView`) is introduced for other screens and happens to help them too.

## 2. Data-layer amendments (beyond the original Task 5 spec)

The original plan's repository sketches are the right shape but under-scope two things the brief explicitly requires: real server-side role scoping (no full-table-then-filter), and notification triggers wired to real events.

- **`PaymentRepository`** (new — never created): implement per plan Task 5 Step 4 (`observePayments`, `recordPayment`, `confirmPayment`, `rejectPayment`, optimistic-apply/rollback, two-person rule via `PaymentRecord.canBeActionedBy`). **Add** `observePaymentsForTenant(String tenantUid, PaymentsListener)` using `.orderByChild("tenantUid").equalTo(uid)` — a real query, not a client-side filter of the full node. This is what Tenant's Payments/History screens (plan Task 16) must use instead of the plan's own "filtered client-side" wording, which is exactly the anti-pattern the brief prohibits.
- **`TenantRepository`**: add `observeTenant(String uid, TenantListener)` (single-node read, not in current code) for Tenant's own Dashboard/Details, and `setPresence(String tenantUid, PresenceStatus, long now, Callback<Void>)` for the Yupo/Hayupo overdue-presence buttons (neither exists today; both are referenced by plan Tasks 10/11/15 as if already present).
- **`ShopRepository`**: add `observeShop(String shopId, ShopListener)` (single-node read) so Tenant's Details screen fetches only its own shop, not the full `observeShops()` list.
- **`NotificationRepository`** (new — never created): implement per plan Task 5 Step 5 (`observeFor(uid)`, `push`, `markRead`, `markAllRead`) — already correctly designed to query `notifications/{uid}` directly, i.e. genuinely user-scoped at the repository level, not a UI filter.
- **`AppNotification` model**: add `relatedShopId` (String) so rows can deep-link to a shop, and a new type constant `TYPE_TENANT_FLAGGED_GONE` (Hayupo presence pick) alongside the existing seven types.
- **Overdue-notification dedup** (brief §17): before `OverdueCheckReceiver` pushes a `TYPE_OVERDUE` notification for a tenant, check whether an unread `TYPE_OVERDUE` notification already exists for that `(userUid, relatedTenantUid)` pair created after the tenant's current `dueDate` — if so, skip the push. This lets the 3×/day alarm (08:00/14:00/18:00, intentionally repeating while overdue, per the mockup's own note) keep firing without also creating duplicates from an opportunistic on-app-open check.
- **Real business-event triggers to wire** (brief §16, none exist today): `confirmPayment`/`rejectPayment` → push `TYPE_PAYMENT_CONFIRMED`/`TYPE_PAYMENT_REJECTED` to the tenant; `TenantRepository.setPresence(HAYUPO)` → push a management notification (`TYPE_TENANT_FLAGGED_GONE`) to admins/super admin; `OverdueCheckReceiver` → push `TYPE_OVERDUE` to both the tenant and their assigned admin(s) (via `UserRepository.observeAdminForShop`, plan Task 15).

## 3. Execution sequence

One task at a time, stopping to commit and report after each (per standing preference — no unsupervised cascading through the list). Order follows dependency, not brief-section order:

1. **Repository layer**: `PaymentRepository`, `NotificationRepository` (new), plus the additions in §2 to `TenantRepository`/`ShopRepository`, plus the `AppNotification` model additions. No UI yet.
2. **Admin/Super Admin Dashboard** (plan Task 9): `AdminDashboardFragment`, `StatusBadgeView`, `PaymentsAdapter`, `ConfirmRejectSheet`, `RecordPaymentSheet` — the actual record→pending→confirm/reject workflow, wired to `PaymentRepository`.
3. **Properties retrofit** (plan Task 10, applied to the existing `PropertiesFragment`/`ShopAdapter`): wire the Yupo/Hayupo overdue-presence prompt (currently absent) via `TenantRepository.setPresence`; confirm stats (units/occupied/empty/overdue) and All/Occupied/Empty/Overdue filters are computed from live data, not hardcoded.
4. **Tenants retrofit** (plan Task 11, applied to the existing `TenantsFragment`/`TenantAdapter`): gate registration to Super Admin (§1.3), add the same Yupo/Hayupo prompt.
5. **Tenant Dashboard + Details** (plan Task 15): wire real data via `observeTenant`/`observeShop`/`observeAdminForShop` — currently pure inflate-only stubs.
6. **Tenant Payments + History** (plan Task 16, using the query-scoped `observePaymentsForTenant`, not the plan's original client-filter wording).
7. **Admin/Super Admin Notifications** (plan Task 13) + **Tenant Notifications** (plan Task 17), sharing one `NotificationAdapter`/`item_notification.xml` per the plan's own note to move it to `ui/common/`.
8. **Notification delivery** (plan Task 18): real `NotificationHelper`/`OverdueCheckReceiver`/`NotificationScheduler`, the dedup rule from §2, and the event triggers from §2's last bullet.
9. **Top-bar bell + badges** (new, §1.2): unread-count badge on `btnNotifications` for all roles; tap routes per role as decided; `SuperAdminNotificationsActivity` for the one role with no nav tab.

Each numbered item above is one commit-sized task; I'll stop after each for review before starting the next.

## 4. Testing

Per the original plan's stated constraint (no emulator/instrumented runner reliably available), the same split applies: pure logic (dedup key computation, notification-type-to-copy mapping, if any is extracted as a plain function) gets a JUnit test; everything touching Fragments/Firebase is verified by `./gradlew :app:assembleDebug` (via the WSL2 recipe in `[[project-maduka-android-app]]` memory) plus manual screen-by-screen comparison against the mockup, one role at a time, per the brief's own §23 test plan.
